# Super Computer Use 体验评审与优化建议

日期：2026-11-03。范围：AI 操控的速度、流畅度、准确度、预览与操作特效。

这是一份评审建议，未修改产品代码。评审开始时工作区已有 6 个修改文件，予以保留。

## 结论

现有后台 AX 操作、窗口范围、差分观察、批处理、截图常驻进程、暂停机制和视觉层值得继续保留。下一阶段最有价值的工作是把这些能力接成一致的执行闭环：**确认目标 → 执行动作 → 等待所需状态 → 返回证据，同时展示真实动作反馈**。

建议顺序：修复反馈断点与观察时序 → 解决预览长等待 → 加强目标身份与坐标一致性 → 减少模型往返和进程启动 → 打磨连续预览与动画。

## 证据范围

- 实际使用 Codex 自带 Computer Use 打开本机 Super Computer Use 控制台，查看概览、诊断、截图，并返回概览。
- 实时界面显示两个权限已授权、服务运行中、DSH 最近调用成功。这不能证明所有宿主、应用与任务都已可用。
- Codex 本轮接口实际支持持久应用对象、AX 差分、组合动作后观察、截图与 AX 联合观察；界面状态变化时曾拒绝继续使用旧状态，要求重新读取。
- 读取了 Codex Chrome 接口的本轮能力说明：同一浏览器接口同时提供 AX 路线与 Playwright 定位器路线；未操作用户浏览器标签内容。
- 阅读仓库 JS 适配层、Swift 引擎、Python MCP 和相关测试；通过已有测试调用安装的引擎操作隔离 demo 窗口。
- 本文不声称掌握 Codex 未公开内部实现，也没有进行同一模型、同一任务的 Codex/SCU 性能对跑。README 的历史性能数字没有在本轮重测。

## 1. 优先修复动作特效的连接问题

**已通过模拟工具调用复现。**

`lib/index.mjs:568` 的 `clickVisualPoint()` 依赖缓存节点的 `x/y/w/h`；`lib/core.mjs:834` 的 `recordSnapshot()` 只保存 `ref/role/title/windowId`。因此以控件 ref 调用 `cu_click` 时，无法获得光标位置。

本轮同一模拟控件调用结果：

| 路径 | 发出的视觉事件 |
|---|---|
| `cu_click(ref)` | 无 |
| `cu_click(x,y)` | cursor、label、ripple |
| `executeBatch` 内坐标 click | 无 |

批处理直接调用 `exec()`，也没有复用单步工具的光标和涟漪逻辑。现有测试主要验证视觉辅助函数本身，未覆盖 ref 点击到视觉层的完整连接。

建议先补齐 ref 的几何信息，并让单步和 batch 共用动作事件。最终落点应以执行引擎刚解析的控件位置为准；缓存坐标用于预提示时要带快照版本，不能当成永久真值。

视觉事件分成“定位目标”“动作已派发”“结果已验证”“失败”。目前涟漪在 `manager.exec()` 前触发（`lib/index.mjs:711`），可能出现失败动作也先闪点击效果。涟漪可以表示派发，成功状态必须等结果证据。

验收：ref 点击、坐标点击、batch 点击均有一致反馈；过期目标、动作失败和取消不显示成功；文字显示“点击「导入」”，避免把 `k0.3.2` 作为用户主文案。

## 2. 统一动作后的等待与验证

**代码确认，尚未进行真实慢加载应用复现。**

DSH 的 `runPostAction()`（`lib/index.mjs:583`）动作后立即做一次 snapshot；`buildCommandArgv("snapshot")` 默认 `--max-settle-walks 0`（`lib/core.mjs:310`）。它没有注释所说的变化驱动重读。窗口、搜索结果或弹窗稍晚出现时，这次观察可能过早。

Python MCP 的 `observe_after()`（`engine/mcp/server.py:1159`）已有早观察、未变化时等待剩余预算再观察的逻辑，默认预算 350 ms。相同引擎通过不同适配层，等待语义并不一致。

建议把共同语义放到引擎/统一执行服务：

1. 动作前确认目标存在、属于正确窗口、可操作。
2. 确定性的输入和快捷键可连续执行。
3. 遇到界面跳转时等待明确条件，例如输入值匹配、文件对话框出现、搜索结果包含目标。
4. 默认返回紧凑差分；需要确认任务结果时使用明确后置条件。
5. 重试观察，避免在结果不明时重放点击或提交。

“任意树变化”只能作为重新观察的信号，不能证明目标操作成功；计时器或加载动画也会改变树。可以先采用有上限的条件轮询，再在支持的应用中利用 AX 通知唤醒，保留轮询回退。

Apple 提供 [AXObserverAddNotification](https://developer.apple.com/documentation/applicationservices/1462089-axobserveraddnotification) 注册界面通知。浏览器端可借鉴 [Playwright 的动作可执行性检查与自动等待](https://playwright.dev/docs/actionability)。这些是实现参考，并非 Codex 内部实现说明。

已有 `engine/mcp/execution.py` 实现动作前后断言和观察轮询，但文件明确注明未接入 MCP；`StateInspection.swift`、`state_adapter.py` 也未进入生产主调用链。应先接通有明确后置条件的少数常用流程，避免重新造一套重复执行器。

## 3. 把预览长等待从动作返回路径中移开

**实测现象与源码支持；根因仍需分段计时确认。**

本轮 `npm test` 的插件复合用例通过，但总耗时约 19.91 秒。实时诊断日志中，两次 `shot` 前分别出现约 8 秒、9 秒空档。这是包含会话、截图、点击、批处理与清理的完整用例，不能当作单次点击耗时。

源码中：

- `runPostAction()` 等待 `Promise.all(observeTask, previewTask)`，可选预览也会决定返回时间。
- 截图 daemon 的一次 capture 等待上限为 8 秒（`engine/Sources/main.swift:2094`）。
- JS daemon 请求超时默认 12 秒（`lib/core.mjs:546`），失败后还会尝试另一条截图路径。
- 获取 `SCShareableContent` 使用无超时的 `sem.wait()`（`engine/Sources/main.swift:2071`）。

上述机制与长等待现象相符，但本轮未记录 daemon 每个阶段，不能直接认定是某一个超时造成。

建议分别记录排队、窗口枚举、截图、编码、附件保存、fallback 的耗时和实际使用路径。先给可选预览设置短预算和明确降级：动作及 AX 结果及时返回，预览显示暂不可用或稍后刷新。若下一步必须依赖截图定位，则必须等待新截图，不能把过期画面当作当前证据。

面向观看体验，可以在“观看操作”模式里提供独立的低帧率窗口预览；模型仅在关键节点接收图像。用户观看刷新率与模型图像输入频率应分开计量，避免每刷新一帧就增加模型上下文。

## 4. 加强控件身份、截图坐标和多屏一致性

**代码风险，未做真实错点复现。**

当前 `resolveNode()`（`engine/Sources/main.swift:2875`）以子节点路径和可选 role/title 校验目标。同名按钮或列表行重排时，这不足以证明仍是原来的对象。`buildCommandArgv()` 找不到来源缓存时，也仍可构造 ref 动作。

建议给观察返回 `snapshotId`，目标绑定应用、窗口、快照版本。执行时校验目标身份；无法证明就返回需要刷新，避免静默命中另一个同名控件。常驻进程可保留 AX 对象引用；语义重定位应限定在已知容器且要求唯一匹配。

截图 daemon 缓存 `SCShareableContent`，窗口还存在时直接复用，再使用缓存 `window.frame` 生成 origin/size（`main.swift:2085`、`:2120`）。移动或缩放窗口后存在几何信息过期风险，应单独更新窗口几何，并为截图返回时间戳、显示器、窗口位置、实际缩放率及统一变换。

光标 overlay 当前仅创建在 `NSScreen.screens.first`（`main.swift:2321`），坐标换算也未扣除目标显示器原点。分屏布局使用窗口大小推断屏幕大小（`lib/core.mjs:1154`）。建议读取真实显示器与可用区域，在目标屏幕绘制反馈。

验收覆盖：重名控件、窗口移动、窗口缩放、外接屏负坐标、不同缩放率、窗口关闭重开，以及用户操作后继续执行。

## 5. 降低整个任务的耗时，而非只压缩一个点击

用户等待时间可拆成：模型思考/往返 + 执行排队 + 系统操作 + 观察/图像处理 + 失败恢复。

现有 `cu_batch` 已能减少模型往返，值得优先完善。批量单位以“选中搜索框 → 输入 → 回车 → 等搜索结果”这类短流程为宜；界面发生分支或加载时应设置检查点。

`runEngine()`（`main.swift:3415`）对 windows/frontmost/cursor 有直接路径，但点击和快照等仍创建子进程。可以逐步迁移高频动作到可重启的常驻 worker，保留故障隔离与监督；先量化收益，再扩大迁移范围。

HTTP 服务在单一队列处理请求（`main.swift:3539`），慢请求也可能拖慢状态查询和 HTTP 暂停。保持写操作有序，同时给停止/取消与健康查询独立处理入口。多客户端场景需要服务端控制权，而非仅依赖某个 JS manager 的队列。

仓库已有 `ControlLease.swift` 和 `ProcessSupervisor.swift` 原型及测试，但没有主调用链使用；租约文件也明确只管理本进程状态，接入后仍需处理服务重启和遗留子进程。

本轮模拟调用还复现了 deadline 缺口：预算 20 ms 的单步骤 batch 执行约 82 ms 后仍返回 `ok:true`。`lib/core.mjs:1033` 仅在还有后续步骤时检查该类超时。应分开返回“动作结果已知”和“超出预算”，并把 deadline/取消传播到执行层；已确认的动作结果不应因为超时被抹掉。

## 6. 让模型获得足够的信息，并降低工具使用负担

当前 `isImageCapableRoute()`（`lib/index.mjs:62`）在模型不支持图像或能力解析失败时返回 false，截图将保存为路径，不能据此认为模型已看到图像。剪映时间线等 AX 信息稀疏界面，视觉能力会明显影响可达到的效果；本轮没有确认用户当前 DSH 模型是否支持图像。

建议在诊断页明确显示“当前模型能否看图、最近一次图片是否送达、当前使用 AX/OCR/视觉哪条路径”。不支持图像时如实返回能力限制，避免让模型猜时间线坐标。

工具层可以保留现有工具，同时提供绑定目标的轻量会话：首次选定应用和窗口后，后续动作复用目标，减少重复填写 pid/windowId。保留必要的层级、可执行动作、焦点和选择状态，按需展开大树；不要为了省 token 删除决定操作方式的信息。

浏览器场景继续使用现有 browser-skill/DOM 路线，并与桌面会话统一目标与反馈。文本控件优先语义定位；画布区域使用截图定位；各路径都返回同样的执行/观察/验证状态。

## 7. 视觉体验应跟随真实动作

建议保留现有 Core Animation 与非激活 overlay，统一由动作事件驱动，而不是继续增加独立定时器和装饰层。

| 状态 | 用户看到的反馈 |
|---|---|
| 模型正在判断 | 胶囊显示“正在判断下一步”，光标静止 |
| 定位目标 | 控件短暂描边、虚拟光标移动 |
| 动作已派发 | 对应位置涟漪，输入框边缘轻亮 |
| 等待应用 | 显示“等待导入窗口”等具体条件 |
| 验证完成 | 简短完成反馈，然后自然淡出 |
| 失败/暂停 | 停止动画，显示失败原因或接管状态 |

动画参数可先试：光标移动 80–160 ms、涟漪 180–280 ms、完成后约 300 ms 淡出，再通过录屏调整。这些是设计起点，尚未实测优于现状。当前光标移动 280 ms、涟漪 500 ms；快速 batch 下应合并已经过时的视觉事件，从当前 presentation 状态继续动画，避免积压。

默认突出目标窗口、光标和状态胶囊；全屏边缘光适合录制演示模式。提供减少动态效果选项。特效不进入动作的阻塞路径，也不覆盖下一步需要点击的控件。

## 8. 建立可比较的验收集

先固定小规模任务集：原生文本输入、Finder 文件对话框、Electron 搜索、浏览器表单、剪映素材导入与时间线选择。对不同模型/宿主分别记录结果。

建议每个任务重复至少 20 次，先建立基线；以下指标是候选验收目标，不是本轮实测成绩：

| 指标 | 初始目标 |
|---|---|
| 用户收到首个状态反馈 | P95 < 100 ms |
| 热路径本地动作 + AX 观察，不含模型与必要的应用加载 | P50 < 300 ms，P95 < 700 ms |
| 可选预览失败 | 约 500 ms 内明确降级，不拖住动作结果 |
| 停止 | 100 ms 内反馈；拒绝新动作，明确展示在途动作收尾状态 |
| 控件与坐标身份变化 | 基准集中无静默错目标；无法确认时要求重新观察 |
| 动作完成报告 | 必须有相应观察证据，不用 `ok:true` 代替业务成功 |
| 视觉层 | 录屏无明显跳点、积压、残留；与动作事件一致 |

同时记录任务成功率、模型调用次数、图像字节数、输入 token、人工接管次数，以及失败发生在哪一层。比较不同模型时必须固定工具和任务；比较引擎版本时必须固定模型、提示和应用状态。

`package.json:62` 的默认 test 只运行 core.test.mjs，遗漏了上述其他 Node 测试。建议把纯逻辑与桌面集成测试分组，默认检查覆盖所有纯逻辑测试，并同步分屏行为的产品约定与测试。
