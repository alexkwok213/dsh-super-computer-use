## 2. 优先修复的发现

### F1 · P1：跨应用参数会混用旧会话的窗口

位置：`lib/index.mjs:933`，`engine/Sources/main.swift:5470`。

`resolveTargetArgs()` 分别填充 pid 和 windowId。会话绑定 A（pid=42, window=7）时，调用方明确传 B 的 pid=99、未传 windowId，输出却成为：

```text
click --x 5 --y 6 --pid 99 --window 7 --background
```

本轮用真实工具定义和模拟执行器复现此参数组合。Swift 坐标点击随后用 windowId 的 owner 覆盖 targetPid，因此存在把 B 的操作送给 A 的路径。没有对用户业务窗口实施错点实验。

修复建议：把应用/窗口作为一个整体目标解析。只有调用方没有指定新目标时才继承会话；指定新 pid 时重新查其窗口或保持应用范围，指定 windowId 时校验/解析其 owner。引擎遇到 pid/windowId 不一致应拒绝，避免静默覆盖。

验收：会话 A→显式 pid B、显式 window B、多窗口同应用、不匹配 pid/window 均有测试；任何一项都不能向 A 误派发。

### F2 · P1：读队列仍被慢请求挡住，落实报告的 8 ms 结论不成立

位置：`engine/Sources/main.swift:3749`、`:3881`。

现实现先把所有连接送入 `queue.async`，读取请求后才决定转交 `readQueue`。POST 的 `handle()` 在这条串行队列中同步执行，所以其后的 GET 连分类都要等待。

本轮真机重复三次：先发约 2.4 秒的只读 expect，300 ms 后查询 status。

| 轮次 | 空闲 status | expect 期间 status |
|---|---:|---:|
| 1 | 5 ms | 2358 ms |
| 2 | 8 ms | 2255 ms |
| 3 | 4 ms | 2264 ms |

慢操作仍会使控制台看起来卡住。HTTP pause 同样留在写队列；本轮未触发全局暂停，不能引用上表当作暂停实测。

修复建议：在进入动作串行队列前完成有上限的读取与分类。只让动作执行排队，健康查询和取消走独立通路；共享状态仍需同步。必须同时覆盖“慢 POST 已开始后到达 GET”的时序。

复现：`node docs/reviews/service-read-probe.mjs`。只创建自带 demo，执行只读等待与状态查询，结束关闭 demo。

### F3 · P1：预览超时返回后，仍会拖慢下一次动作

位置：`lib/index.mjs:203`、`:249`、`:265`、`:294`。

存在两个不同缺口：

1. `Promise.race` 只停止等待，没有停止 capture 流程。超时后杀掉 daemon，它的 promise 结束，capture 接着执行 engine fallback，把 `shot` 加入动作共用队列。本次答案很快返回，下一次动作却被遗留截图挡住。
2. 预算仅包住获取像素，模型能力解析与 `attachments.saveImage()` 在预算外。附件保存变慢时，“600 ms 预览预算”不能约束整体耗时。

本轮模拟真实异步顺序复现：20 ms 预算返回降级后，调用序列为 `key → shot → key`；下一次 key 被模拟截图额外阻塞约 **131 ms**。另一个用例获取像素立即成功、附件保存 130 ms，20 ms 预算最终仍用约 **131 ms** 并返回 preview.ok=true。

修复建议：为一份预览创建独立 deadline/取消上下文，检查每一次排队和 fallback 是否已经失效；超时后不允许再提交 fallback。预算覆盖附件处理，但宿主 API 无法取消时允许它自行收尾，禁止迟到结果覆盖新帧状态。显式截图仍可使用独立、更长的预算。不要把动作与可选预览放进同一个阻塞队列。

验收同时测“本次调用延迟”和“预览失败后的下一次动作延迟”，并覆盖排队超时、附件服务卡住、迟到结果与会话切换。

### F4 · P1：snapshotId 尚不能证明点击时仍是原控件

位置：`lib/core.mjs:1135`，`lib/index.mjs:947`，`engine/Sources/main.swift:3020`。

当前 token 只是插件 `recordSnapshot()` 的递增序号。若应用自己重排，而插件尚未再 snapshot，序号保持不变，检查会通过。引擎仍以 path + role/title 解析，两个同名控件可以互换后继续通过。

现有 identity 测试主要覆盖“插件已取过第二次快照，但调用方还拿第一次的 token”，没有覆盖“外部界面已改变，插件不知道”。本轮模拟后者，动作仍派发；这证明适配层缺少这类失效检测，不是对真实应用错误点击的实测。

修复建议：把客户端观察版本和真实目标身份分开。对可获取稳定标识的控件校验应用、窗口、标识与容器；在常驻观察进程保留 AX 对象并校验身份；无法证明时重新解析唯一语义目标或拒绝。仅增加截图时间戳、重复读取相同标题、或强制传 snapshotId 都不能解决同名身份交换。

是否迁移执行 worker 可以继续由测量决定，但“保留目标身份需要常驻观察状态”是独立的架构需求，不能只用一次 spawn 的 50 ms 成本来否决。

### F5 · P1：当前基准不能证明“0 ms 反馈、停止很快、任务全部成功”

位置：`bench/run.mjs:37`、`:111`、`:128`、`:165`、`:212`、`:224`。

- `autoSession:false`，click 测试没有启动视觉会话；没有实际 overlay 可以呈现首帧。
- 传给任务的是动作前 `overlay.slice()` 的拷贝，新事件不会进入这个数组。
- `firstFeedbackMs=null` 随后经 `Number(null)` 变成 0。报告的 0 ms 实际是“没有测到”。即使修复数组，也只能测到命令写出，不能代表屏幕已经显示。
- click 只要求 `ok:true`，没有断言计数器真的增加；batch 无后置条件。它们的 20/20 是工具层成功，证据不足以当作业务成功率。
- 输入反复追加同一个 `bench`，用 `query:"bench"` 检查子串；后面的输入即使没落字，也可能被之前遗留的文本满足。每轮只停止会话，没有重置文本。
- stop 用例不启动在途动作，也不进行分屏，未等子进程退出、窗口恢复或控制权释放；0–1 ms 是函数返回，不能证明“停止全部操控”。
- `llm` 与 attachments 是 mock，模型名仅占位；此脚本完全没有调用模型，无法拿来比较模型或不同宿主的端到端体验。
- 输出只保留聚合与少数失败注释，丢掉每轮 timing/证据；即使任务失败，最后仍 `process.exit(0)`。

修复建议：保留现有微基准但准确命名。缺失值保留 null；记录独立外层时钟、实际执行路径、原始样本、成功证据与构建身份。输入使用每轮唯一值与精确匹配；点击验证计数变化；停止测试覆盖在途动作和窗口恢复，区分“UI 已响应”“不再接受新动作”“在途动作已收尾”。任何基准失败时返回非零退出码。

新增真实模型+宿主+应用的端到端任务集，另行记录工具调用次数、任务完成时间、首次正确动作、重试和人工接管。不要混成一个速度数字。

### F6 · P2：关闭边缘光没有在渲染层生效

位置：`lib/index.mjs:79`、`:379`，`engine/Sources/main.swift:2035`、`:2071`、`:2489`。

`rim:false` 只阻止插件发送 aura=true；原生 overlay 收到 cursor/click/label 仍无条件调用 `pulseAura()`。`setAura(false)` 只是当时淡出，没有保存禁用状态。配置默认值实际仍为 true，也与落实报告“默认只保留目标高亮+光标+胶囊”不同。

本轮提取当前源码的真实 `CursorLayerView`，离屏执行：

```json
{"rimDisabledOpacity":0.0,"rimAfterActionOpacity":1.0}
```

修复建议：显式把启用状态送入 overlay，由渲染层统一检查；减少动态效果也应覆盖持续呼吸光。多屏布局最好每块屏独立 overlay，当前并集窗口的标签夹紧仍可能落入屏幕之间的空隙。

复现：`python3 -B docs/reviews/native-view-probe.py`。该检查不开桌面窗口；没有测量真实刷新率或 GPU 帧时间。

### F7 · P2：默认会话仍重复预热，与新补丁目的相反

位置：`lib/index.mjs:571`、`:574`。

默认省略 preview 时，`args.preview !== true` 让 warmCapture=true，同时 `args.preview !== false` 又执行真实预览。因此只有显式传 `preview:true` 才跳过预热，最常用的默认路径仍然多抓一张图并排队。

本轮模拟 `cu_session({action:"start",pid,windowId})`，同时观测到 warmCapture=true 和 preview 实际执行。

修复建议：先计算唯一的 `shouldPreview`，预热条件直接使用它的反值。验收覆盖 preview 省略、true、false 以及无目标窗口。

### F8 · P2：会话目标缺省与工具 schema 不一致

位置：`lib/index.mjs:698`、`:1065`。

`cu_snapshot`、`cu_expect` 的 pid 仍标为 required。工具执行函数虽然支持从会话继承 pid，真实宿主若先校验 required 就无法走到该逻辑；测试直接调用 execute 绕过了这层。

修复建议：统一 schema、说明、运行时校验，或提供显式会话工具。用宿主参数校验路径执行“只传 ref/query 的会话调用”，不要只直调 execute。

## 4. 下一轮怎样进一步做快、做顺、做好看

### 第一阶段：消除偶发卡住和错目标

按 F1 → F3 → F2 → F4 → F5 排序。F6/F7/F8 是较小且可独立验证的修复。先完成这些再重新生成基线，保留所有失败样本。

把一个动作的状态统一为：目标已确认、动作已派发、等待应用、结果已验证、已失败/取消。分别返回派发结果和业务结果，并让光效、胶囊与工具输出使用同一事件序列。

### 第二阶段：把模型与系统操作连接得更紧密

以短任务为执行单位，如“填入搜索词→提交→等结果”；已知动作连续执行，分支处返回新观察。减少每个小动作都重新思考的轮数，同时保持条件验证。

针对原生控件、浏览器 DOM、Electron 与画布分别选路径；对同一目标复用缓存，对不确定区域才截图。逐步评估常驻 AX 观察/执行 worker，测收益时算完整任务中的重复启动次数、状态复用和尾延迟，不只算单次 fork。

候选验收：持续会话中已知三步任务只需一次工具调用；原生本地动作+有效观察热路径 P95 < 300 ms（不含模型与应用必要加载）；超时预览不能拖慢下一次动作；停止控制请求在负载下仍能快速响应。这些是后续目标，不是当前成绩。

### 第三阶段：做连续的观看体验

建议增加“观看操作”的独立窗口预览：模型按需接收关键帧，用户看连续画面。先试 10–15 fps 的目标窗口流，静止时降频、忙碌时升频；实测 CPU、内存、功耗后再定参数。Apple 的 [SCStream](https://developer.apple.com/documentation/screencapturekit/scstream) 提供应用/窗口的视频捕获能力，能作为实现基础；并不保证在本机当前宿主上下文中直接可用，仍需验证回调与生命周期。

光标动画建议保持现有 140 ms 起点，但让涟漪与实际派发事件对齐；batch 下跳过已经过时的定位动画。从 presentation 状态继续动画是合理方向，[CALayer 官方说明](https://developer.apple.com/documentation/quartzcore/calayer/presentation())确认它提供正在显示的动画值。该机制已使用，不需要另造动画引擎。

目标窗口轻描边、语义动作短标签、输入时字段轻亮、等待时明确说明条件；完成后自然淡出。用户接管时视觉状态立即变化，恢复时从新观察继续。演示模式可开启边缘光，日常模式突出局部反馈。衡量“酷”的标准包括能否看懂、是否遮挡、是否与真实动作同步、长时间观看是否疲劳。

### 第四阶段：建立能支持对外比较的任务集

先选 5 类应用、约 20–30 个真实任务：原生文本编辑、Finder 文件对话框、Electron 搜索/列表、Chrome 表单、剪映素材与时间线。使用隔离样例素材与固定起始状态，每项先做 20 轮。

分开发布两组结果：本地引擎微基准，以及真实模型/宿主的端到端完成率与任务时间。固定屏幕布局、应用版本、模型、提示、网络、图像预算、冷/热状态；记录调用数、首次正确动作、截图量、重试和接管次数。成功必须由任务目标证据判定。

当前证据足以说明这一版在本机 demo 上有明显改善；不足以宣称“全网最快”或“达到所有应用中的 Codex 效果”。

## 5. 复现与未覆盖项

`second-review-probes.mjs` 包含 6 个纯模拟复现。其断言用于确认当前缺口仍存在，不能把这些断言通过当成验收通过；修复后应把相应条件转换为正常回归测试。

`service-read-probe.mjs` 是本机服务真机测试；`native-view-probe.py` 编译当前视图类离屏检查。脚本不发送消息、不修改业务文件、不切换连接或权限设置。

未覆盖：真实 DSH 大模型端到端调用、其他 MCP 宿主、同名控件重排的真实应用错点、多显示器真机组合、连续帧率/功耗、全链路在途取消、长时运行、竞品同条件对跑。本轮没有把这些标为完成。
