# 性能与体验改造方案

目标：把 cu 做成"最快、最流畅、最精准"的 computer-use——单步延迟进入 100ms 级，并且提供 Claude/Codex 那种"宿主窗口让位 + 被控窗口画中画预览"的体验。

本文只记录**实测 + 代码位置 + 方案选择**。数字来自 2026-10-30 本机实测，未测项明确标注。

---

## 一、结论先行

四层开销，按影响排序：

1. **每次工具调用 fork 一个 `cu` 进程**——约 40ms 固定税，且 AX 连接、窗口缓存、截图上下文全部冷启动。这是"反应慢半拍"的地基。
2. **截图每次都新起 `screencapture` 子进程**——250–380ms，客户端统计均值 **2268ms**（含大窗口编码传输）。
3. **`observe` 默认睡 350ms 再跑一次全量快照**——`click` 均值 585ms 里有相当一部分是"点完自己再花约 500ms 看一遍"。
4. **AX 快照每节点 3 次 IPC**——children / 9 属性批量 / actionNames，节点上限 800、深度 24。

另有几处零碎但真实的卡顿：`launch_app` 单次 **15.4s**（`semaphore.wait()` 无超时）、`bring_on_stage` 固定 550ms、点击/打字后一串固定 `usleep`。

---

## 二、逐项根因

### 2.1 fork 税（影响：所有工具，恒定 ~40ms）

链路：`mcp/server.py:run_cu` → HTTP `/v1/exec` → `Sources/main.swift:runEngine` → `Process()` 起子进程 → 读管道。

`/v1/call` 名义上是"进程内派发"，但它的 `batch` 与非 batch 两条分支最后都调用 `runEngine`（`main.swift:2657`、`main.swift:2670`），同样 fork。

**测量佐证**：`frontmost` 本身是微秒级操作，经服务端 `/v1/exec` 实测 **42ms**；`windows`（含一次约 40ms 的 CGWindowList 扫描）实测 **65–82ms**。差额 ~40ms 就是 fork + exec + HTTP 往返 + 进程冷启动。

### 2.2 截图（影响：最重，250–2268ms）

服务模式下强制走 CLI：`runEngine` 给子进程设 `CU_SHOT_CLI=1`（`main.swift:2475`），`shot` 命令据此强制 `cliCapture` → `/usr/sbin/screencapture`（`main.swift:2724`）。代码注释自述 250–380ms。

原因是 TCC 按进程归属：守护进程没有自己的屏幕录制授权，且 SCK 的 completion 在 launchd agent 里不触发（`main.swift:2718` 注释）。

菜单栏 app（`local.cu.app`）**持有授权**，但现有代理路径是 DistributedNotificationCenter + 临时 PNG 落盘再读回，600–700ms。

### 2.3 observe（影响：click/type 的"感觉延迟"）

`observe_after`（`mcp/server.py:1124`）：`time.sleep(observeMs 默认 350ms)` → 再跑一次 `snapshot`（实测 494ms）。

所以 `click observe=true` ≈ 585 + 350 + 494 ≈ **1.4s**。用户感知到的"点完半天没反应"主要来自这里。

### 2.4 AX 快照（影响：snapshot 494ms 起步，大应用 1250ms）

`snapshotNodes`（`main.swift:1891`）每节点：

- `orderedChildren` → 1 次 IPC（level 0 上还额外每子元素 5 次 `stringAttribute` 排序键，窗口多则更贵）
- `multiAttributes` → 1 次 IPC（9 属性批量，这块已经优化过）
- `actionNames` → 1 次 IPC

`actionNames` 只有"要按这个控件"时才需要，纯读取时是纯浪费。

参考值：TextEdit 快照 **1250ms**，`ax --find` **300ms**。

## 三、目标指标

| 指标 | 现在（实测/统计） | 目标 |
|---|---|---|
| 常规调用（frontmost / guards） | 42ms | < 8ms |
| `click` | 585ms 均值 | < 100ms |
| `snapshot` | 494ms 均值，TextEdit 1250ms | < 150ms |
| `screenshot` | 250–380ms，均值 2268ms | 50–80ms |
| `click` + observe | ~1.4s | < 200ms |
| `launch_app` | 15.4s | < 2s（并给超时） |

## 四、三条路线

### 路线 A：内核直连（纯减法，1–2 天）

把 `switch args.command` 重构成 `func runCommand(_ args: Args) -> [String: Any]`，让 `emit` 写入每请求独立的缓冲而不是 stdout；服务端 `/v1/call` 直接调用它，不再 fork。

- **收益**：所有工具抹掉 ~40ms 地板；AX 连接、窗口列表缓存、`prepareAX` 状态常驻；顺带可以把 `actionNames` 改成按需拉取，`snapshot` 再降一大截
- **风险**：`fail()` 是 `Never`（内部 `exit(1)`），要改成抛错；改动覆盖全部 switch 分支（约 1500 行），必须用现有 `tests/server_units.py` 等做红绿兜底
- **不动的东西**：MCP 工具语义、坐标约定、安全层全部不变

### 路线 B：常驻帧 + 画中画（最接近你描述的体验，2–3 天）

菜单栏 app 里跑一条常驻 `SCStream`，用 `AVSampleBufferDisplayLayer` 自己渲染——**这就是"旁边的小窗口预览"**。

- 截图从"起子进程拍一张"变成"取最新帧"：50–80ms
- 顺带产出 PiP 面板：贴在被控窗口角落，实时显示，带"停止"按钮
- 会话开始时把**宿主窗口**（Claude/Codex/Qoder）缩到边角，会话结束还原——`move_window` 已经完全后台实现，只缺编排
- **风险**：常驻流有 CPU 成本，必须能按需开关、无会话时零开销

### 路线 C：事件驱动（锦上添花，3–5 天）

`AXObserver` 订阅目标 app，动作后主动推变化，不再轮询快照；预取下一帧。

- **收益**：observe 成本趋近 0
- **风险**：AXObserver 在 Chromium/Electron 上不稳，需要保留轮询回退

---

## 五、建议顺序

**A 先做，B 紧随，C 最后。**

A 是纯减法、可测、风险可控，做完所有工具立刻快一档；B 才是你真正想要的那份"体验"——画中画 + 宿主让位 + 帧级响应，而且它依赖 A 打下的常驻进程基础；C 收益递减，等前两条稳定再说。

## 六、待确认

1. **Claude / Codex 的实际做法**没有核实到——本次内核与搜索工具被权限分类器阻塞，未能联网确认它们是"缩小宿主窗口"还是"独立画中画面板"，也没确认它们是否用常驻流。恢复后应补查。
2. 常驻 `SCStream` 在**多显示器 + Stage Manager** 下的帧获取稳定性未测。
3. `launch_app` 15.4s 那次是冷启动还是 LaunchServices 卡住，未分离测量。
