# CU 项目经验沉淀（对话记录整理）

来源：2026-10-29 ~ 10-30 与 AI 的多轮实操对话。这份文档记的是**为什么这样决定、踩过什么坑、怎么验证**；现场事实与待办看 [协作记录.md](协作记录.md)，工具与拒绝词看 [README.md](README.md)，非技术版用法看 [使用说明.md](使用说明.md)。单次排障的完整过程见 [对话档案-2026-10-29.md](对话档案-2026-10-29.md)（前台被占用、接入验证、提示条生命周期）。

## 一、用户定的硬约束（每次动手前先对齐）

1. **后台优先**：「这个 cu 的操控一定要在后台，不占用我的鼠标控制权和界面控制权」。任何会抢前台的动作（`bring_on_stage`、前台点击）都要先征得同意，且用完把焦点还回原应用。
2. **别拿用户正在用的应用做验证**：不重启、不做破坏性点击、不为了测试把他的窗口切到前台。验证一律用引擎自己开的 demo 窗口。
3. **不做伪装订阅鉴权**：把免费态伪造成付费态这条路不做。
4. **配置里不放凭据**：MCP 连接器配置不写 token；网关目录（含凭据）不上传不提交不分享。
5. **对外交付物是规格**，不是打过补丁的官方包；本仓库代码全部自写，只用苹果公开接口（Accessibility / CoreGraphics / ScreenCaptureKit / Vision）。

## 二、架构决策与理由

| 决定 | 为什么 |
| --- | --- |
| 引擎二进制**就是 App 的主程序** | 早先 LaunchServices 拒绝自编译 Mach-O（`-10825`），真因是 swiftc 默认 deployment target 比本机新。`build.sh` 显式 `-target arm64-apple-macos14.0` + 真实证书签名后不再需要脚本壳 |
| 常驻服务跑**包外的一条硬链接**（同一 inode） | 进程在包内会被 LaunchServices 当成 App 本人，`open` 就会去激活服务（它不接 UI 事件）→ `-600`「应用程序不再打开」。硬链接既只有一份引擎，又给了服务一个包外身份 |
| MCP 代理放在 `~/Library/Application Support/cu/mcp/` | 稳定路径。仓库可以整体挪位置（本次就从 `cu-standalone/` 移到了 `work/computer-use/`），已接入的 agent 一个都不用重配 |
| 菜单栏 App 同时是**权限锚点**和**截图代拍者** | launchd 代理里 ScreenCaptureKit 的异步回调永远不回来；App 是有 UI 的进程，能拿到自己的屏幕录制授权，于是截图可以委托给它 |
| HTTP(127.0.0.1:47777) + MCP 双入口 | 权限只授一次、状态集中可见、参数集中管理；各家 AI 应用都来连同一个网关 |

## 三、TCC（macOS 权限）实战经验

这一段最费时间，结论都记下来：

1. **陈旧记录会死锁**：系统设置里开关是开的，但实际鉴权失败，而且**不会再弹新授权窗**。解法是清掉重来：`tccutil reset Accessibility local.cu.app`、`tccutil reset ScreenCapture local.cu.app`（不需要 sudo）。
2. **App 和服务的授权互相独立**：给 `Computer Use.app` 授权 ≠ 给包外那份 `cu` 授权。所以服务启动时也要自己弹一次授权（`service` 分支启动 +2s 调 `requestPermissionsIfMissing()`）。
3. **屏幕录制必须重启进程才生效**：授权后圆点不会自己变绿，`launchctl kickstart -k gui/$(id -u)/local.cu.service`。
4. **在别的终端里探测权限不可信**：从 Qoder 的 shell 跑 `cu perms` 会被归因成 Qoder 自己的授权，返回 true 而实际是 false。**只有 launchd 服务的 `/v1/status` 才是权威读数。**
5. **每次重装换签名都可能清掉屏幕录制授权**（辅助功能一般能保住）。所以：不要为了小改动反复 `install-app.sh`；攒够一批再装。
6. 缺授权时主动弹系统对话框（`AXIsProcessTrustedWithOptions(prompt)` / `CGRequestScreenCaptureAccess()`），和 Claude 一样；菜单里留一个「弹出授权窗口」兜底。

## 四、后台物理边界（实测出来的，不是猜的）

- **控件自己的 `AXPress` 不依赖窗口合成** → 台前调度（Stage Manager）的离台缩略图窗口也能后台点。这是后台能力的地基。
- **离台窗口收不到键盘事件**，按 pid 投递的 unicode 也进不去 Chromium（即使该应用是前台）。所以「后台打字/后台回车」做不到，只能：`tryOffstage` 投递后**读回应用状态验证**，没变化就如实报 `off_stage_window`。
- **离台后 Chromium 会把不可见内容剪出 AX 树**：实测聊天窗口回到离台状态，侧栏标题、`已完成 9s` 还读得到，但助手回复正文搜不到了。读长回复要么让它在台上，要么改用截图。
- **锁屏时整棵网页 AX 树收起**，只剩菜单栏；`snapshot` 返回 `count:0`。这不是引擎坏了，判断前先确认前台是不是 `loginwindow`。
- **Electron 输入框的三条路**（按顺序试，每条都读回验证）：AXSelectedText 插入 → AXValue 写入 → **应用自己的右键菜单「粘贴」**（`AXShowMenu` + 菜单项 `AXPress`，全程后台，剪贴板先备份后还原）。第三条是 WorkBuddy 唯一能写进去的。
- **聊天类提交用回车，不要点那个灰按钮**：实测即使用真实键盘把字打进 DOM，WorkBuddy 的「发送」仍然是 `enabled:false`（应用的 aria 噪音）；`key --name return` 一发就中。

## 五、「假成功」是这类工具最贵的 bug

今天所有返工几乎都源于一次「工具返回 ok，但应用里什么都没发生」。落地的对策：

| 机制 | 作用 |
| --- | --- |
| `control_disabled` 拒绝 | 禁用控件的 `AXPress` 是空操作，直接拒绝而不是报成功（可 `force` 跳过） |
| `tryOffstage` + 读回验证 | 离台窗口照常投递，但只有应用自己的状态变了才算成功 |
| `expect` 断言工具 | 按 ref 或文字定位控件，断言 `enabled`/`value`/`contains`，轮询到超时。做完一步用它确认 |
| 离台坐标点击拒绝 | 坐标事件打到未合成的窗口会凭空消失，原来却报 `ok` |
| `landed` 字段 | `type`/`paste` 返回是否真的落到焦点控件 |

对照官方：Claude 自己的提示词里就写着「computer-use 工具会报成功，但下一张截图显示什么都没变」——所以它的循环是**动作即观察**。这也是我们加 `expect`、并计划做 `observe` 的理由。

### 2026-10-30：剪映导入的界面语义

- **打开面板里双击文件夹等于导入整个文件夹**，不是进入。本轮因此两次误启动大任务（31484 项、277 项），都在进度 0 时取消。浏览目录只单击；进入目录走 `Cmd+Shift+G` 前往完整路径。
- **进度弹窗是独立窗口**：`导入素材` 是单独的 AXWindow，不在主窗口 AX 树内，窗口级截图也拍不到。判断导入是否卡住必须用整屏截图或应用级查询；错误地把主窗口截图当成全部现场会误判。
- **批次返回 ok 不等于路径生效**：`Cmd+Shift+G → 点“关闭”清空 → 输入路径 → 回车` 依赖前一步真的完成；关闭点击落空时，新路径会追加到旧路径，回车失败且导入按钮禁用。在关键步骤间插入一次读树做等待和验证，并在提交前核对字段值、按钮可用。
- 前往面板的“关闭”按钮会清空输入但保留面板，是可重复的清空方法；`Cmd+A` 在 AX 设置值后并不能可靠清空。

### 2026-10-30：把导入步骤做成一次调用（ImportFlow）

- **标签随版本变**：本机打开面板的前往标签是「前往：」，不是「前往文件夹」。查询用子串「前往」能同时覆盖两者；写死完整标签会在某个版本上直接失败（本轮干跑第一次就是这样失败的）。
- **清空必须点「关闭」再读回字段**：现场再次复现，不清空直接 AX 写入会把新路径追加到上一次路径后面（`…/16_手机收尾.mp4/tmp/…/验证片段.mp4`），回车后「导入」保持禁用。提交前校验字段值**完全等于**目标路径，不一致就重来一次。
- **验收信号是状态，不是按钮存在**：回车后等「导入」`enabled: true`；点击后唯一成功信号是素材库出现对应条目。`ax --find` 每个查询最多 25 条，统计条目要按 `AXButton` 去重，不能拿原始匹配数当条目数。
- **按编码名查条目**：条目标题里的文件名是 `quote(name, safe="")` 的百分号编码（大写十六进制、`%2C` 分隔字段）。用这个编码当查询词，比按整库前缀翻页更准，也不受 25 条上限影响。
- **作用域**：打开面板和前往 sheet 在窗口作用域就能查到；“请选择媒体资源”是一个标题为空、`value` 为该文字的 `AXStaticText`。只有窗口作用域查不到时才退到应用作用域（进度窗必须应用级查）。
- **速度账**：干跑单文件约 11.8s、18 次引擎调用；单次 AX 查询 0.15–2.3s，大头是整树遍历和回车后等按钮变可用（2–3 次轮询）。省下的是每个文件 5–6 次模型往返，不是让应用本身变快。
- **提交语义**：每个文件只点一次「导入」；结果不明时用素材库核实，绝不重复提交；首个失败即停并收起面板。

### 2026-10-30：状态适配与控制权的教训

- 状态读取和状态适配各有边界：适配器只能检查传入的目标信息和已声明的完整性，不能自行证明 AX 元素身份或文件集合完整。生产路径必须先提供可靠证据；读取不到就保持 unknown，不把缺失当成空集合。
- 截图返回 `ok` 不等于图像可用：Stage Manager 离台窗口拍到的是缩略图尺寸的整窗预览，不能当正常画面读细节；长时间空闲后的首次 ScreenCaptureKit 调用还可能超过 4 秒超时。判断前先看返回的尺寸、内容和目标窗口是否在台上。
- 执行、暂停共用串行队列时，慢操作会阻塞暂停；给单进程加租约也不能管住直接 CLI、本地 fallback 或重启后残留的子进程。接入前必须统一写入准入并确认在途操作结束，不能把原型当成桌面级互斥。
- 子进程收到终止信号不等于已经退出；确认不了时必须保留未决状态，不能让下一个任务接管。直接子进程退出也不能证明后代退出或鼠标、键盘和剪贴板状态恢复。超时应使用单调时钟；单调等待不能消除发信号时 PID 复用的竞态。本机核查还发现 Foundation 在终止回调运行前就已回收子进程，按进程号补发信号前必须先取得独占回收权或明确后备，不能只靠 `isRunning`。
- 本轮状态适配器、租约和子进程监督原型及相关测试通过，但尚未接入服务或 MCP，未验证真实文件面板、截图或端到端速度。详细验证范围见协作记录。

## 七、验证方法学（下次照做，别再重新发明）

1. **只用引擎自开的窗口做验证**：`cu demo` 会开一个带输入框/计数按钮/密码框/滚动区/**16 层深视图链**的窗口，随便点、随便拖、随便缩放都不碰用户的东西。
2. 现成脚本：`tests/server_units.py`（代理逻辑）、`tests/guards.py`（安全层 dry-run）、`tests/deepfind.py`（深树搜索回归）、`tests/demo_controls.py`（控件级）、`tests/window_ops.py`（窗口操作）、`tests/stability.py` / `background.py`（重复稳定性）、`tests/verify_unlock.py`（解锁后一键体检）。`tests/run_all.sh` 串起来跑。
3. **测试前先清残留进程**：`pkill -f "bin/cu demo"`。本次就是两个残留 demo 实例让「双击失效」看起来像回归，实际是取错了 pid。
4. 测试脚本里的判定要看**应用的可见状态**（值、计数、按钮标题），不要看工具的 `ok`。
5. 一次全绿的假象来自顺序串扰：`demo_controls.py` 里 Sheet 还没关就测 `scroll`，会拿到 `ok:false`——单独复测才是真相。

## 八、部署与回滚

```sh
./build.sh          # 只编译，不装机（调试用）
./install-app.sh    # 打包 + 装 /Applications + 同步 server.py/tools.json + 重启服务与菜单栏
```

- 安装脚本会**重启服务和菜单栏进程**：别人正在用 CU 时别擅自跑。
- 服务读工具清单的路径是 `~/Library/Application Support/cu/mcp/tools.json`（相对引擎的 `../mcp/tools.json`），改 schema 必须同步这里，否则 `/v1/tools` 和实现会不一致（本次就漏过一次）。
- 卸载：`launchctl bootout gui/$(id -u) ~/Library/LaunchAgents/local.cu.service.plist` 与 `local.cu.menubar.plist`，删两个 plist 和 `/Applications/Computer Use.app`。

## 九、这次对话里踩到的具体坑（小但费时间）

- **Qoder 连接器更新**：`manage_app_mcp` 的 `update` 只接受 `action + serverId + expectedSourceRevision + config`，多带 `entryKey/scopeKind/name` 会报 `MCP_INPUT_INVALID`。
- **批量脚本改文件要事后校验语法**：用正则往 `mcp/server.py` 的 schema 里插字段，8 处插成了孤立逗号，直接把文件弄坏。教训：批量插入后立刻 `python3 -c "import ast;ast.parse(...)"` + 跑单元测试。
- **`pbcopy` 会改用户剪贴板**：走剪贴板粘贴前必须先备份、结束还原（引擎的 `pasteText` 已经这么做）。
- **`cu` 不带参数会当成启动菜单栏 App**：在 shell 里手滑跑一次，会多起一个实例；被 kill 掉还会留下脏的 LaunchServices 状态。
- **MCP 工具的参数名容易猜错**：`set_value` 用 `text`、`perform_action` 用 `name`、`ax_find` 用 `query`。先 `mcp_get` 看 schema。
