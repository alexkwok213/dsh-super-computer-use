# 对话档案：前台被占用与接入验证（2026-10-29）

这份档案记录一次完整的排障对话：用户报告「用 CU 时前台一直被占，没法用别的应用」，到根因定位、修复、实测，再到后续「让 AI 客户端直接调用 CU」的接入验证。现场事实与最新待办以 [协作记录.md](协作记录.md) 为准，通用设计经验见 [经验沉淀.md](经验沉淀.md)，本档案保留**这一次的推理链和测量数字**，便于以后复现。

## 一、用户的原话与真实诉求

> 「我发现你用我开发的这个 COMPUTER USE 时，为什么一直占用我的前台，导致我没法用其他」

表面是「为什么」，实际要的是「修好」。用户的底层约束和项目里已有的一条一致：CU 必须在后台工作，不占鼠标、不抢前台，操作结束要把焦点还回去。

## 二、症状与第一轮误判

第一反应会怀疑「点击/输入是不是切了前台」。实测否掉了这个方向：引擎的点击默认走 `postToPid`，不激活目标、不动光标；`move_window` 直接设窗口属性；`read_text`、`paste_text` 走 AX 插入。这几条路径在 focus probe 里逐个跑过，前台一次都没变。

真正偷前台的是两处与「操作」无关的东西：

1. **自动操作药丸（capsule）**。MCP 第一次操作某个应用时会 spawn 一个 `cu capsule` 进程。它是新启动的 AppKit 进程，而 macOS 会激活任何新启动的 `NSApplication`。面板本身是 `NSPanel` + `[.borderless, .nonactivatingPanel]` + `canBecomeKey=false`，这些属性**挡不住进程级激活**。结果是一个没有窗口可接管键盘的进程占着「当前应用」，用户的输入落进空处。
2. **安装脚本用 `open` 启动 App**。`open`（即使 `-g`）对已在运行的 `LSUIElement` App 是发一次 reopen，走 `applicationShouldHandleReopen` → `showConsole` → `NSApp.activate(ignoringOtherApps: true)`。所以每次装完，控制台窗口会自己弹到用户面前。

测量证据：胶囊用 `--seconds 4` 跑一次，22:21:15 起前台从 Terminal 变成 `cu`，直到 22:21:19 才还回来。生产环境的 TTL 是 900 秒——也就是说用户可能被一个空壳进程占住 15 分钟。

## 三、修复

### 3.1 把焦点还回去，而不是指望面板不激活

在初始化 AppKit **之前**记下前台 pid，窗口挂上之后立刻交还：

```swift
let previous = frontmostBeforeLaunch()   // 必须在 NSApplication.shared 之前
...
panel.orderFrontRegardless()
stayInBackground(previous)
```

`stayInBackground` 先尝试 `NSRunningApplication(processIdentifier:).activate()`（macOS 14+），失败再 `NSApp.deactivate()`；并在 0.25 秒、0.8 秒各补一次，因为窗口服务器给回焦点不是同步的。

`runCapsule` / `runHalo` / `runCover` / `runMenuBar` 四条路径都加了这个捕获。

### 3.2 菜单栏 App 自己判断「这次激活是不是误激活」

菜单栏进程没有窗口，被意外激活时不该抱着焦点：

```swift
func applicationDidBecomeActive(_ notification: Notification) {
    guard consoleWindow?.isVisible != true, !openSettingsAtLaunch else { return }
    stayInBackground(lastFrontPid != 0 ? lastFrontPid : launchFrontPid)
}
```

`lastFrontPid` 由 `NSWorkspace.didActivateApplicationNotification` 维护。用户主动点「控制台…」或 `--settings` 启动是合法路径，不在此列。

### 3.3 安装不再用 `open`

`install-app.sh` 改为 `launchctl print` 判断 agent 是否在跑，不在就 `launchctl kickstart -k`，最后才退回 `open -g`。launchd 启动不会激活任何东西。

### 3.4 顺带修掉 launchctl 竞态

原来的 `install-service.sh` 是 `bootout` 紧接着 `bootstrap`。`bootout` 是异步的，`bootstrap` 落在卸载过程中会失败（`Input/output error`），而脚本把错误吞进了 `>/dev/null 2>&1 || true`。表现是：装完菜单栏 ● CU 消失、47777 端口不通、`launchctl list` 显示 `-  -15`。

修法是等 label 真的消失再 bootstrap，失败再 kickstart 兜底：

```sh
launchctl bootout "gui/$(id -u)" "$plist" >/dev/null 2>&1 || true
while launchctl print "gui/$(id -u)/$label" >/dev/null 2>&1; do sleep 0.2; done
launchctl bootstrap "gui/$(id -u)" "$plist" >/dev/null 2>&1 || \
    launchctl kickstart -k "gui/$(id -u)/$label" >/dev/null 2>&1 || true
```

另一个连带教训：安装脚本结尾那一次 `curl /v1/status` 可能是空的，因为服务冷启动比 15 秒更慢。**一次空响应不等于服务挂了**，要用重试探针确认。

## 四、怎么证明修好了

`tests/focus_probe.command`：每 0.4 秒用 `lsappinfo front` 采一次前台应用，依次跑基线、`launchctl kickstart` 重启菜单栏、spawn 胶囊、`windows` / `snapshot` / `frontmost` 三条服务调用，同时用 `cu windows` 检查有没有冒出「Computer Use」窗口。

最后一轮结果（22:40:08–22:40:23）：前台全程是 Terminal，一次没变；没有出现任何控制台窗口；服务 `ok:true`、`accessibility` 与 `screenRecording` 均为 true、`nextSteps` 为空、pid 92107。

胶囊是否真的画出来，不能用 Claude 自己的截图验证——它会把 `local.cu.app` / `cu` 的窗口过滤掉。要用引擎自己拍：`cu shot --screen --region 1360,0,368,96 --out tests/capsule_shot.png`，看到深色药丸「焦点测试 · 自动操作中」加一个 × 才算数。

## 五、第二次对话：让客户端直接调用 CU

用户关掉了 Claude 自带的 computer use，希望直接调自研的 CU。这里要分清两件事：

- **CU 有 MCP 服务**（`mcp/server.py`，36 个工具）和 **HTTP 入口**（127.0.0.1:47777）。能力是有的。
- **当前会话没有加载它的工具**。MCP 工具是会话建立时注入的，改代码、改配置都不能往正在跑的会话里塞新工具。关闭自带工具也不会自动切换。

所以卡点不在 CU 功能，而在「接入是否真的生效」不可观测。

### 5.1 原来的状态是假阳性

`agentsCatalog()` 里：

- Qoder 的 `configPath` 是 `nil`，于是 `wired` 直接为 `true`——从未验证过；
- 其他客户端只要配置文件里有 `computer-use` 就算「已接线」；
- 只要有一个同名进程活着且没有 `closed` 标记，就算「已连接」。

配置存在 ≠ 客户端加载了工具；进程活着 ≠ 会话能用。这和项目里那条「假成功是最贵的 bug」是同一类问题，只是发生在接入层。

### 5.2 改成四段证据

MCP 侧在协议处理里打三个时间戳：

| 字段 | 何时写入 | 说明 |
| --- | --- | --- |
| `initializedAt` | 收到 `initialize` | 客户端握手成功 |
| `toolsListedAt` | 收到 `tools/list` | 客户端主动来要工具清单，通常是会话真正加载了工具 |
| `lastSuccessfulCallAt` | 工具调用成功 | 唯一能证明「这个会话能调」的证据 |

同时修了 `lastOk` 的判定：原来用 `bool(result.get("ok"))`，而 MCP 成功返回的是 content 信封、没有 `ok` 字段，会被误判为失败。现在是 `not isError and result.ok is not False`。

状态因此变成：`● 调用已验证` / `● 已请求工具清单` / `◐ 已握手` / `◐ 已配置·待连接` / `○ 未验证接入`。菜单栏和控制台共用同一套文案，不再各有各的说法。

### 5.3 顺手修掉的两个真 bug

- **Claude Desktop 和 Claude Code 被混为一谈**：两者进程名都以 `Claude` 开头，`spec.processes` 的前缀匹配会把 Claude Code 的调用算到桌面版头上。现在用 clientInfo、可执行路径和 `claude-code` 关键字区分。
- **配置文件损坏会被覆盖**：原逻辑读不出来就当空对象，然后写回——用户的 `mcpServers` 直接没了。现在解析失败就报 `error` 并保留原文件；写入改成 `createDirectory` + 原子写。

## 六、测试纪律（这次最该改的是我自己）

用户问了一句「为什么这测试花了这么久」。复盘：

1. 每个验证写一个 `.command`，用 Finder 打开 → **每次都新开一个终端窗口**。一次会话留下 15 个。
2. 大量固定 `sleep 40`、`sleep 50`，而不是轮询到条件满足。
3. 同一个检查重复跑（重编译、重启、再验证各来一遍）。

改法：

- 新增 `bash tests/run_all.sh --quick`：只跑 MCP 逻辑测试，不编译、不开窗口、不碰 UI。
- `tests/install_verify.command` 作为唯一的安装入口：编译 → 装 → `cmp` 比对已安装副本 → 快速测试 → 轮询 `/v1/status`，全部写进一个日志。
- `run_all.sh` 从 `sh` 改成 `bash -o pipefail`：原来的 `python3 tests/x.py | tail -2` 会把失败吞掉，只留下尾部两行。

还有一条环境约束值得记：这台机器上 Terminal 是 click 级（不能打字、不能按键）。`.command` 跑完 Terminal 会变成前台，下一批 `cmd+shift+g` 会被拦下——必须先 `open_application("Finder")` 再发键。

## 七、第三次对话：提示条的生命周期

用户说「这个 COMPUTER USE 打开的窗口后，都不关，留下太多窗口」。这里要把两类窗口分开：

- **终端窗口**：测试脚本留下的，属于我这边的问题，已逐个关闭（15 个）。
- **药丸**：原来 spawn 一次 `--seconds 900`，即使客户端已经空闲，也会挂 15 分钟「正在自动操作」。

药丸改成跟随操作：

- 每次工具调用结束起一个 2 秒的守护定时器，到点就终止本连接创建的提示进程；
- 连续调用之间不会闪；
- 下一次调用重新 spawn；切换目标应用时先收起旧的，保证同时只有一个；
- 连接退出（`atexit`）时取消定时器并清理。

关键边界：**只终止自己创建的进程**（`AUTO_SESSIONS` 里的子进程 + 校验 `poll()`），绝不按名字杀进程、绝不关用户的应用窗口。用户的文档、浏览器、终端不会因为任务结束被自动关闭。

新增 `tests/indicator_lifecycle.py` 覆盖四点：只杀自己且活着的子进程、同一应用复用活着的提示、提示退出后能重建、退出时取消待执行清理。

## 九、可复用的结论

1. **新起 AppKit 进程一定抢前台**，面板属性拦不住；正确做法是记住原前台并在挂窗口后交还，必要时补一次延迟交还。
2. **不要用 `open` 启动已安装的 `LSUIElement` App**，它会触发 reopen 逻辑；用 `launchctl kickstart`。
3. **`bootout` 是异步的**，紧接着 `bootstrap` 会失败并且静默把 job 弄丢；要等 label 消失。
4. **「配置好了」和「能调用」是两件事**，必须用协议层的握手、工具清单和成功调用三种证据分层展示。
5. **测试入口要收敛**：一个安装入口、一个快速入口，其余用轮询而不是长 sleep；否则验证本身会变成用户看到的「一直占着窗口」。
6. **指示灯要跟随操作**，不要用长 TTL 冒充「会话中」；清理只能针对自己创建的进程。
